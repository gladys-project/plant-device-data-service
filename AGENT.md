# plant-device-data-service guidance

This is the configuration and message-contract skeleton of the Gladys plant device data service. Maven artifact and Spring application name are plant-device-data-service, while the current checkout directory is device-data-service. Preserve existing work and instructions.

Use Java 25 without preview, one Maven module, Spring Boot WebFlux/Reactor, Spring Cloud Stream with the regular Kafka binder, reactive Spring Data MongoDB, Lombok and SLF4J. Pin the Boot/Cloud BOMs and unmanaged plugins/images. Let Boot manage compatible dependency and test versions. Use constructor injection when classes need dependencies. Prefer Boot auto-configuration over custom Kafka/Mongo factories. Do not introduce blocking MongoDB clients, Spring MVC or Reactor Kafka.

Follow TDD: write a meaningful test, run it and confirm its expected failure, then implement the smallest passing change. Report actual executions only. Apply DRY and KISS: share configuration defaults, avoid duplicate constraints and speculative interfaces, services, repositories, controllers or frameworks. Keep packages limited to useful code. Update relevant tests and documentation with changes.

The authoritative OpenAPI inbound definition is src/main/resources/openapi/kafka-device-data.yml. It matches the device-data-processor outbound KafkaDeviceData envelope and diagnostics, with an embedded DeviceError schema so builds are independent. Generate Java DTOs during Maven generate-sources, with generated Jakarta validation annotations. Never edit or commit generated target/ files. Device ID remains the intended Kafka key. The user authorized KafkaDeviceDataMapper: use MapStruct 1.6.3, Spring component model, constructor injection and ERROR policies for unmapped source/target properties. Map every inbound field to the mutable internal DeviceData class; copy diagnostics and preserve numeric schemaVersion=1 rather than enum ordinal. Keep the internal DeviceData free of MongoDB annotations. Use mutable DeviceStateDocument and DiagnosticHistoryDocument classes with fixed IDs and Spring Data reactive repository interfaces. Copy the DeviceData observation when mapping it into a document. Keep generated mapper code in ignored target/. Do not add sensor payload, soil resolution, an outbound contract or additional transformations without a later request.

The user-authored configuration selects onDeviceDataEvent and declares onDeviceDataEvent-in-0 for gladys.device.data.v1 with a dedicated group. Preserve autodetection disabled and consumer auto-startup false in every profile; do not register or activate a processing function. Preserve the user-authored listener draft. PlantDeviceDataService exposes processDeviceData(DeviceData) and registerDevice(UUID, String), both returning Mono<Void>, and diagnosticHistoryDocument(UUID, int) for real-device history. Request validation belongs in the API layer. First-observation inserts use the compound identity and a null initial version. Registration and renaming look up all existing entries by UUID alone and save the name and REGISTERED state on each. Keep the listener inactive. Observation updates, diagnostic reconciliation, battery evaluation, notification publishing, watering and pump logic require a later request. The deployed profile enables the standard MongoDB health indicator; it does not enable consumption.

Keep standard connection settings under spring.kafka.* and spring.mongodb.*. Spring Boot 4 uses spring.mongodb.uri. Keep Spring Cloud binding settings under spring.cloud.*. Never enable automatic production topic creation or partition changes. MongoDB index auto-creation stays disabled. Use ReactiveMongoTemplate and the reactive driver; Boot owns client lifecycle. Keep request/event paths free of .block(), .join(), sleeps and blocking broker/database operations. Regular Spring Kafka/Cloud bindings do not provide end-to-end reactive backpressure.

Run ./mvnw test for Docker-independent fast checks and ./mvnw clean verify for all checks including Kafka/MongoDB Testcontainers integration tests. Docker is mandatory for *IT; do not silently skip. Use bounded waits, test-only provisioning and fixtures, and StepVerifier for real reactive publishers. Integration test documents and Kafka records must stay in tests. Tests import shared YAML defaults with isolated test addresses and close test consumers; context/container lifecycle closes other resources.

Expose only health/info. Default health does not probe MongoDB; deployed health does. Secrets stay outside Git, logs and images. .env.example contains placeholders only; Spring does not automatically load env files. Reuse /etc/gladys/gladys.env for server Compose interpolation and explicitly forward only this service's settings. Do not overwrite an existing server env or print connection credentials. Root Compose manages only this service, joining the external gladys network; Kafka/MongoDB are independent infrastructure. No commits, pushes, deployments or remote repository renames are authorized by the skeleton request alone.

Persistence models live under persistence.model and reactive interfaces under persistence.repository. DeviceIdentity(deviceId, mock) is serializable and separates test/real state. Use standard MongoDB UUID representation, @Version on device state, and @MongoId literal string history IDs. History IDs are caller-supplied per transition, not source event ID alone. Preserve bounded, deterministic device-scoped history paging and the declared history index; production auto-index creation stays disabled. Do not introduce automatic migrations/TTL, deduplication rules or error-resolution assumptions. Tests must verify BSON mapping, mock isolation, stale-save rejection and history paging against real MongoDB. Service tests cover its public/private API, first-observation insert, the existing-device path and save error propagation.

CI, deployment and release workflows follow the Gladys processor pattern. Use the Linux self-hosted runner, immutable action SHAs, Java 25, Docker-required clean verify and pinned Compose in each job that uses it. Reuse the verified JAR for deployment and release. Deploy only on a PR merge into main or a manual branch dispatch. Serialize deployments without interrupting one in progress. Update only the plant-device-data-service Compose project and use PLANT_DEVICE_DATA_IMAGE with the verified commit SHA. Reuse the shared server env file and preserve its read-only Docker fallback and private temporary copy. Keep Kafka, MongoDB and the external network under independent management. Do not deploy or publish a release just to check workflow changes.
